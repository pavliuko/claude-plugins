## 2026-08-25 [skill-suggestion] — 2.1.0

- `config.logActivations` and `config.logPath` are now real. Both keys sat in a consumer `rules.json` (`BulkSource-iOS-SECOND/.claude/skill-suggestion/rules.json`, pointing at `.claude/logs/skill-suggestion.log`) while the hook kept writing `.claude/skill-suggestion/skill-suggestion.log` — neither the plugin nor the pre-plugin local hook it replaced (consumer commit `f9a0e77b`) had ever read them. Reported by a peer Claude session in that repo; user chose "implement both keys" over deleting the dead config.
- Both keys are read **per scope from that scope's own file**, not from the merged config — user request confirmed the recommendation "per scope, relative to scope root". A relative `logPath` resolves against `~/.claude/` for user rules and `$CLAUDE_PROJECT_DIR/` for project rules; `~/…` and absolute paths are used as written. Reason: the merged, project-wins alternative would let a project silence or relocate the user log and break the existing invariant that a user-scope-only setup never creates `.claude/` directories inside projects. Defaults are unchanged (`skill-suggestion.log` next to each scope's `rules.json`), so existing installs log exactly where they did.
- `logActivations: false` is checked with an explicit `== false` test rather than jq's `// true` — the alternative operator treats `false` as missing and would have made the switch impossible to turn off.
- Unknown `config` keys (and unknown `config.scoring` keys) are now logged once per run as `⚠ Unknown config key in <scope> rules: <key>`. User picked "log warning line" over silent (current) and stderr. This is the mechanism that would have surfaced the dead keys above months earlier.
- `read_rules()` moved above the log setup in `lib.sh` because log resolution now needs it; no behaviour change.

## 2026-08-17 [skill-suggestion] — 2.0.0

- **Breaking:** the skill-entry flag renamed from `"always": true` to `"required": true`. The config key was the last place still calling these "always" skills while every user-facing surface — banner header, `Status:` line, log lines, transcript notice, README section — had settled on "required" since 1.2.0. User request: "change rules config key from always to required". Major version because a `rules.json` written for 1.1.0–1.5.0 silently stops pinning: an unrecognised `always` key is simply ignored, so the skill drops into normal scoring and, with no `promptTriggers`, scores 0 and vanishes. Fix is a one-word edit per entry.
- No dual-key fallback. Accepting both names is the kind of compatibility shim that outlives the reason for it, and this plugin's only consumer is the author's own machine — the live `~/.claude/skill-suggestion/rules.json` was migrated in the same change.
- Internal vocabulary aligned with the key: `skill_is_pinned` → `skill_is_required`, `PINNED_SKILLS` → `REQUIRED_SKILLS`, and the "pinned" wording removed from comments and log lines (`⊘ Pinned (delivered at SessionStart)` → `⊘ Required …`, `No pinned skills` → `No required skills`). Grepping for one word now finds the whole feature; before this, "pinned", "always", and "required" each found a third of it.
- Also reworded in the model-facing footer: "pinned by the user's config" → "required by the user's config". This is the one rename that changes what Claude reads, not just what the maintainer reads.

## 2026-08-17 [skill-suggestion] — 1.5.0

- `hook.sh` split into three files: `lib.sh` (sourced, shared), `require-skills.sh` (`SessionStart`), `suggest-skills.sh` (`UserPromptSubmit`). 1.4.0 served both events from one 531-line script branching on `hook_event_name` in five places. User request: "split the script", after asking why it wasn't split and being shown the shared/split line counts — the decision was theirs against my recommendation to keep one file, and the argument was that ~130 lines of shared infrastructure outweighed 7 lines of branching.
- The line counts came out better than that argument predicted: 213 + 66 + 259 = 538 versus 531, so the split cost 7 lines, not the duplication I warned about. `lib.sh` holds what both events genuinely share — the two-scope merge (union, project-wins, config deep-merge, `origin` tagging), the `enabledPlugins` gate, `render_skill`, and the envelope — plus two new predicates, `skill_is_available` and `skill_is_pinned`, which absorbed the branching that used to be inline.
- Fixed a real bug the split exposed: the envelope hardcoded `hookEventName: "UserPromptSubmit"`, so the `SessionStart` hook added in 1.4.0 was announcing itself under the wrong event name. Now `emit_envelope` takes the event as its first argument, and the self-check asserts each script names its own event. Worth noting how it surfaced — one script serving two events made the wrong value invisible, since the hardcoded string was right for the case it was written for.
- Also dropped from `render_skill`: the `confidence`/`emoji`/`score_label` triple collapsed into one `confidence` string, since all three were always set together and re-joined at the `printf`.
- Self-check rewritten again for the new entry points (25 assertions), including the new event-name case. It invokes the two scripts separately, which is what Claude Code does.
- `lib.sh` is deliberately non-executable (644) while the two entry points are 755, so it's obvious which files `hooks.json` may point at.

## 2026-08-17 [skill-suggestion] — 1.4.0

- Required (pinned) skills moved off `UserPromptSubmit` onto a new `SessionStart` hook, so the block is delivered once at the top of the session instead of on every prompt. 1.3.0 only asked Claude not to *re-invoke* the skill; the ~120-token block itself was still repeated forever, because a `UserPromptSubmit` hook has no other moment to speak. A pin has no prompt-dependent logic at all, so the per-prompt hook was simply the wrong event for it. User request: "can we send message about required skills at the begining of the session in some other hook?".
- Registered with matcher `startup|resume|clear|compact|fork`. `compact` is the one that earns its place: it re-fires after a compaction, re-asserting the pins exactly when they would otherwise have been summarised out of context — the self-healing property that 1.3.0's escape clause was trying to approximate, now provided by the runtime instead of by wording. Confirmed against https://code.claude.com/docs/en/hooks: `SessionStart` supports `hookSpecificOutput.additionalContext` and those five matcher values.
- One script still serves both events, branching on `hook_event_name`, rather than a second script duplicating the two-scope rules merge, the `enabledPlugins` gate, and the renderer. `SessionStart` skips scoring entirely (no prompt to score) and `UserPromptSubmit` skips pins entirely (already delivered), which means the existing banner assembly needed no changes — each section was already conditional on its array being non-empty.
- `SessionStart` stays completely silent when nothing is pinned, instead of reusing the "no matching skills for this prompt" notice — that wording is nonsense with no prompt, and silence keeps an unconfigured install invisible.
- Footer reworded from "as your first action this turn" to "before replying, then keep following it for the rest of the session … skip the call only if it is already in your context", since the block now arrives before any prompt exists. The escape clause is kept for the `compact`/`resume` re-fires, where the skill may still be in context.
- Self-check rewritten around the two events (8 cases): pins only at `SessionStart`, matches only at `UserPromptSubmit`, `compact` re-assertion, silence when nothing is pinned, and both JSON envelopes. Several 1.3.0 assertions had become wrong rather than failing — they asserted pins in a `UserPromptSubmit` run — which is the sort of thing a stale test hides.

## 2026-08-17 [skill-suggestion] — 1.3.0

- The `REQUIRED` block now says to invoke each pinned skill *unless its instructions are already in context from earlier in this session*, and the section header changed from `INVOKE BEFORE RESPONDING` to `MUST BE ACTIVE THIS SESSION`. 1.2.0's unconditional "invoke now, as your first action this turn" made Claude re-invoke the skill on every prompt, reloading a `SKILL.md` that was already in context — ponytail's is a few thousand tokens, so the waste dwarfed the banner's own ~120. User request: "required skill should be loaded once per session, now claude loads it on every prompt. how can we improve that?" → "how about changing the instruction to claude to something like 'must be invoked if still not'?".
- The "already loaded?" check is delegated to the model instead of tracked in the hook, and that is the point rather than a shortcut. Two hook-side alternatives were considered and rejected: a `$TMPDIR` marker file keyed on `session_id` (cheap, but it only knows what was *announced*, and it would stay silent after a compaction dropped the skill's rules — precisely when re-invoking is needed), and a `jq` scan of `transcript_path` for a `Skill` tool_use (accurate, measured at 17ms over a 2.0M transcript, but it grows with session length and depends on a payload field that was never verified). Only the model can see whether the instructions are still in its context, so asking it is both cheaper and more correct. Worth knowing for anyone tempted by the transcript route: the injected banner is itself written into the transcript, so a naive match on the skill name false-positives on the hook's own output.
- Per-entry `Status:` line reworded from `always active, not conditional on this prompt` to `invoke once per session, then stays in force`, so the entry and the footer agree about the lifecycle.
- README warns against pinning a skill that relies on `allowed-tools` or `disallowed-tools`. Both are per-turn: the grant "clears when you send your next message" and re-applies only on re-invocation (https://code.claude.com/docs/en/skills, "Pre-approve tools for a skill" and "Skill content lifecycle"), so for such a skill the new "one load per session is enough" wording silently drops its tool grants from the second prompt onward. `ponytail:ponytail` declares neither, so nothing pinned today is affected — this is documented as a landmine for the next pin rather than fixed in code. Documented over an `"invokeEveryTurn": true` escape hatch because no known pin needs it; the note is the cheaper half of the fix.
- Correction to the reasoning recorded above: re-invoking a pin does **not** reload the whole `SKILL.md`. Claude Code adds a short "already loaded" note when the rendered content is identical, and appends the full body again only when it differs (changed arguments, dynamic-context output). So this change saves a redundant tool call, not the multi-thousand-token reload originally assumed — still worth it, but the payoff is smaller than the entry above implies. Verified against the docs after the fact, at the user's request: "is it true that skill needs to be invoked once per session? research anthropic documentation before answering".
- Deliberately unchanged: the banner is still emitted on every prompt. A `UserPromptSubmit` hook has no other moment to speak, and suppressing it would need the per-session state this entry just argued against. The residual cost is the ~120-token block; the multi-thousand-token re-invocation is what got fixed.

## 2026-08-17 [skill-suggestion] — 1.2.0

- Pinned skills are now delivered to Claude as an instruction rather than a suggestion, across all three output channels. The 1.1.0 pin only won on ordering and its `📌 ALWAYS` label while the banner footer still read "Consider using these skills **if they're relevant** to this task" — the right hedge for a scored guess and the wrong one for a standing instruction, since the whole point of pinning is that relevance is not in question. User request: "pinned skills are not suggestions anymore, we should send it as command to claude to perform. #1, #2, #3 needs to be changed".
- Channel 1 (`additionalContext`, what the model reads): pins moved out of the shared `🎯 SUGGESTED SKILLS` banner into their own `📌 REQUIRED SKILLS — INVOKE BEFORE RESPONDING` section, per-entry `Status: REQUIRED — always active, not conditional on this prompt` in place of a confidence band, closed by an imperative footer ("These are not suggestions. Invoke every skill listed above … as your first action this turn … do not weigh them against the prompt or skip them as irrelevant"). Scored matches keep the softer wording in their own section; each section is skipped when empty, so a pin-only prompt sends only the imperative and never the word "consider".
- Channel 2 (`systemMessage`, what the user sees): split into `📌 Required skills: … · 💡 Suggested skills: …` so the transcript shows which skills were handed over as an order and which as a hint.
- Channel 3 (the log): `📌 Pinned (always)` became `📌 Required (always, sent as an instruction)`, and the single closing `Suggested skills:` line became separate `→ Required (instructed):` / `→ Suggested (optional):` lines. The log is the only record of what was actually sent, so collapsing the two kinds into one line made pin behaviour unverifiable after the fact.
- Dropped the `ALL_SUGGESTED` array that merged pins and matches — nothing needs the combined list now that every channel reports the two separately.
- Fixed a `set -u` crash in the new `systemMessage` builder: `"$SYSTEM_MESSAGE💡 …"` parses the emoji as part of the variable name, so bash aborted with `SYSTEM_MESSAGE💡: unbound variable` on any prompt that had both a pin and a scored match. Caught by the self-check, not by review; `${SYSTEM_MESSAGE}💡` fixes it and the braces are commented as load-bearing.

## 2026-08-17 [skill-suggestion] — 1.1.0

That workaround does match every prompt, but it scores exactly `intentWeight` (3) — the threshold floor — so the pinned skill was permanently rendered last and labeled `🟠 LOW`, reading as the weakest suggestion on screen when it was meant to be unconditional. User request: "instead of this workaround that we've done in the rules.json for ponytail i want to improve this plugin and add the capability to add skills to rules that will always be suggested with a high score".

Exempt from the cap because with the default cap of 3, pinning three skills would push every real match into the "also matched" footer. Skipping exclusions was the user's call over the alternative of letting them veto a pin: "always means always". A pin is still gated by `enabledPlugins` — Claude Code couldn't invoke a disabled plugin's skill anyway.
- Fixed a latent `set -u` crash surfaced by this feature: the display-cap block copied `MATCHED_SKILLS` with `("${arr[@]}")`, which bash 3.2 (macOS stock, per the script's shebang) rejects as an unbound variable when the array is empty. Previously unreachable because the hook exited early when nothing matched; a pinned-only prompt — the common case — now reaches that code with zero scored matches. The block was rewritten guarded, which also let the `DISPLAY_*` intermediate arrays go.
- Extracted the per-skill banner rendering into `render_skill()` so pinned and scored entries share one code path instead of two copies of the same 20 lines.
- Version bumped to 1.1.0 in both `plugin.json` and `marketplace.json` — additive feature, existing rules files keep working untouched.
- Folded in a `systemMessage`-only envelope on the no-match path ("no matching skills for this prompt"), so the user can see the hook ran without anything reaching the model's context. This existed only as an uncommitted edit in the local marketplace clone; committing it upstream is what allowed that clone to be reset and pulled without losing the change.

## 2026-08-04 [statusline]

- Initial addition, as a standalone `statusline/` directory rather than a plugin under `plugins/`. A plugin's `settings.json` accepts only the `agent` and `subagentStatusLine` keys — `statusLine` is not among them (https://code.claude.com/docs/en/plugins-reference, "File locations reference") — so a plugin cannot deliver this config no matter how it's packaged. Pointing user settings at the bundled script directly was rejected as well: `${CLAUDE_PLUGIN_ROOT}` is documented as ephemeral ("changes when the plugin updates … treat it as ephemeral"), so the path would break on every plugin update. That left two shapes — a plugin with an install command copying the script to a stable `~/.claude/` path, or a plain versioned script with manual install steps. User chose the latter: nothing to enable, nothing to keep in sync.
- Two lines split by what the information answers, not by source: line 1 is *where you are* (directory, git branch with staged/modified counts, clickable PR link), line 2 is *what you're spending* (model, effort, context bar, fuel gauge, account). Model and effort started on line 1 and moved to lead line 2 — user request: "make model and effort first item on the second line". Every optional segment disappears cleanly when its source field is absent, since `effort`, `pr`, and `rate_limits` are all documented as sometimes-missing.
- Known consequence of that split: line 2 runs ~118 display columns fully populated versus ~71 for line 1, so it's the one that truncates on a narrow terminal — and status line notifications occupy the right side of that same row. Measured in display columns, not bytes; a naive `awk length()` reports 168 because the block characters are 3 bytes each and the emoji 4. Recorded so the imbalance reads as known rather than accidental.
- Git state is cached 5s per session in `/tmp` keyed by `session_id` rather than a PID — the script re-runs on every assistant message, `git diff` is slow in large repos, and `$$` changes per invocation so it would defeat the cache entirely.
- The account is read from `oauthAccount` in `~/.claude.json`, because the status line payload carries no account fields at all. Left uncached: the file is 92K and a `jq` read measures ~6ms.
- `refreshInterval: 60` is part of the documented install, not optional polish. The reset countdown and git counts are time-sensitive and the event-driven triggers go quiet while a session idles; 60s matches the countdown's minute granularity.
- The 5h rate-limit window renders as a ⛽ fuel gauge: same 10-block bar as the context segment, but filled with what's **left** rather than what's used, and labeled `76% left`. The emoji drove the semantics, not the reverse — once the segment read as a fuel tank, showing consumption inverted the metaphor. User requests: "improve emoji for current session" → "like fuel station emoji" → "since this is 'fuel tank' we should show how much left". The text label "Current session" (itself an earlier rename from "5h") was dropped when the bar replaced it: "change 'Current session' label to same horizontal bar as for context".
- Consequence worth keeping straight: the two bars now fill in opposite directions — 💽 grows with consumption, ⛽ drains — but both are colored by *consumption*, so a nearly empty fuel bar is red, not green. `render_bar` therefore takes the fill percentage and the coloring percentage as separate arguments instead of deriving one from the other. The README explains the asymmetry so it isn't later "corrected" into inconsistency.
- `% left` is computed as `100 - used_percentage` because `rate_limits` exposes no remaining field, unlike `context_window` which has `remaining_percentage`.
- Countdowns under 60s now read `resets in <1m` rather than `resets in 0m`, which looked like a bug.
- Cyan moved from the model/effort segment to the directory name; model and effort now emit no color escape at all. User request: "make model and effort font black like everything else and make current directory/project font blue how it is now for model and effort". Implemented as *absence of color* rather than an explicit black (`\033[30m`) on purpose — the user's terminal is on a light theme where default foreground reads as black, but a hardcoded black would be invisible on a dark background, and status lines render in whatever theme the viewer has.
- Brackets around the model name were dropped when per-section emoji were added — with 🤖 delimiting the segment, `[...]` read as clutter beside six other emoji-prefixed sections. User request: "add: emoji for each section".

## 2026-07-28 [english]

- Initial plugin creation.
